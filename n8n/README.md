# Сценарии n8n

n8n — единственный отправитель сообщений. База ничего наружу не шлёт и не
знает адреса n8n: обратное направление ([ADR-008](../docs/Decisions/ADR-008-event-delivery.md))
снимает вопрос «где хранить вебхук с токеном».

Все вызовы — обычные HTTP-запросы в PostgREST:

```
POST {SUPABASE_URL}/rest/v1/rpc/{функция}
apikey: {JWT роли bot_worker}
Authorization: Bearer {тот же JWT}
Content-Type: application/json
```

**Ключ — роли `bot_worker`, не `service_role`.** У второго остаются все
таблицы (`0024` снимал гранты только у `public`/`anon`/`authenticated`), и
его утечка открыла бы карточки детей всех центров мимо узких функций 0031.

## Сценарий `poll` — раз в минуту

1. `claim_events` → `{"p_limit": 100}`. Пустой ответ — выходим.
2. Для каждого события: `event_messages` → `{"p_event_id": <id>}`.
   - **Ответ пуст** — получателей нет (тип без обработчика, нет шаблона,
     нет родителя). Зовём `notification_skip` с причиной и переходим к
     `ack_events`: тишина в журнале неотличима от «всё доставлено».
3. Для каждого сообщения:
   1. `notification_begin` → `{"p_event_id", "p_recipient", "p_channel",
      "p_subject_id"}`. Последний — `subject_id` из ответа `event_messages`
      (ребёнок, о котором сообщение). Без него два сообщения одному
      родителю о разных детях схлопнутся в одну строку журнала, и второе
      молча не уйдёт (0035).
      **Ответ `null` — не отправлять**: сообщение уже ушло или исчерпало
      попытки.
   2. Если `channel = "telegram"` — `sendMessage` в Telegram Bot API на
      `chat_id` из ответа `event_messages`.
      **Если в ответе есть `action`** (сейчас это напоминание о занятии) —
      добавь к запросу клавиатуру, скопировав поля как есть, ничего не
      собирая вручную:

      ```json
      "reply_markup": {
        "inline_keyboard": [[
          { "text": "{{ $json.action.label }}",
            "callback_data": "{{ $json.action.callback_data }}" }
        ]]
      }
      ```

      Формат `callback_data` разбирает бот, поэтому строку целиком готовит
      база — в сценарии её собирать нельзя (0035).
      Если `channel = "whatsapp_link"` — **ничего не отправляем**: у
      получателя нет бота, кнопку со ссылкой покажет интерфейс. Сразу
      `notification_finish` со статусом `no_channel`.
   3. `notification_finish` → `{"p_id", "p_status": "sent"|"failed",
      "p_error": <текст или null>, "p_text": <отправленный текст>}`.
4. `ack_events` на успешно обработанные, `fail_events` на те, где шаг 2 или 3
   упал целиком.

**Порядок шагов — часть инварианта.** `notification_begin` обязан идти
**до** отправки: строка «после отправки» не защищает от дубля, а доставка
at-least-once (ADR-003). Это единственное место конструкции, которое не
проверяется pgTAP — его держит только этот порядок нод.

### Ветка `voice_summary` — событие `lesson.voice_received`

Голосовая диктовка идёт тем же `poll`, а не отдельным сценарием:
`claim_events` типы не различает, и второй забор конкурировал бы с первым
за те же события.

На шаге 2, увидев `type = "lesson.voice_received"`, **не ходи** в
`event_messages` — ветка другая:

1. `ai_job_begin` → `{"p_event_id": <id>}`.
   **Ответ `null` — не работай.** Событие чужое, устаревшее, уже сделанное,
   терминальное, запись всё равно упадёт (утверждённая заметка,
   архивный ребёнок, отменённое занятие, готовый черновик), подписка
   центра истекла (0051, событие `subscription.voice_blocked`) или
   исчерпан лимит голосовых резюме по тарифу (0053, событие
   `ai.quota_exceeded`; тарифа нет — `null` без события). Сразу
   `ack_events` — и ни одного платного вызова. Оба отказа терминальны:
   после оплаты или смены тарифа диктовку записывают заново.
   В ответе, кроме `file_id`, — `student_goals` (0048): активные цели
   ребёнка `[{goal_id, title, area, sound, stage_title}]` в порядке
   этап→дата→id, не больше 50, и `student_goals_total` — полное число.
   Ничего, что называет ребёнка, там нет — и добавлять нельзя: список
   уходит в OpenAI и в логи n8n.
2. Скачать файл: `getFile` по `file_id` из ответа, затем загрузка по
   `https://api.telegram.org/file/bot<token>/<file_path>`. Тем же токеном
   бота, которым сценарий уже шлёт сообщения.
3. Распознавание речи (язык `ru`). Сразу после ответа —
   `ai_usage_record` с `{"p_kind": "transcribe", ...}`.
4. Резюме. Вход — транскрипт и цели ребёнка из `student_goals`; выход
   строго JSON с `soap`, `parent_summary` и `goals` вида
   `[{goal_id, score}]`. Сразу после ответа — `ai_usage_record` с
   `{"p_kind": "summary", ...}`.

   Блок целей в пользовательском сообщении — построчно
   `goal_id — формулировка (этап, звук)`, и только если список не пуст:
   пустой блок под правилом «бери только из списка» толкает модель
   выдумывать. Прошлые заметки в промпт **не** передаются (0048: отдельная
   задача, если понадобится — только `parent_summary` утверждённых заметок
   этого ребёнка; `soap` и `raw_transcript` — никогда, там имена соседей
   по занятию).

   **Ответ запрашивается структурированным** (строгая схема, а не «верни
   JSON, пожалуйста»): иначе модель заворачивает его в markdown-блок, и
   запись падает. Это самый вероятный отказ всей ветки, и строгая схема
   снимает его почти целиком.

   Два требования к промту, которые нельзя опускать:
   - **шкала 0–100 названа явно** — иначе модель вернёт свою, 0–5 или
     0–10, и весь прогресс уедет к нулю;
   - **запрет называть кого-либо, кроме ребёнка заметки.** На групповом
     занятии специалист скажет «Бекжан отвлекался, поэтому с Айсулуу
     успели меньше», и это уедет в резюме для родителя Айсулуу.
5. `ai_write_lesson_note` → `{"p_event_id": <id>, "p": <JSON модели>}`.
   В ответе `note_id`, `student_id`, `chat_id`, `progress_written` и
   `progress_skipped` — список целей, по которым оценка **не** записана
   (специалист уже поставил свою). Его стоит дописать в сообщение: иначе
   человек будет уверен, что записалось всё.

   **Фильтр целей перед вызовом — именованный инвариант (0048 Р8), как
   и порядок узлов.** В SQL его нет, pgTAP его не проверит; ошибка здесь
   стоит всей оплаченной диктовки: выдуманный `goal_id` даёт 22P02, чужой
   — 42704, оба откатывают заметку целиком, `ai_job_fail` ставит терминал.
   Буквально, между разбором ответа модели и вызовом RPC:

   ```js
   // Нормализация ДО try: catch не должен трогать то, чего может не быть.
   const studentGoals = Array.isArray(job.student_goals) ? job.student_goals : [];
   const goalsTotal = Number(job.student_goals_total) || studentGoals.length;
   const allowed = new Set(studentGoals.map((g) => g.goal_id));
   const parsed = model && typeof model === 'object' ? model : {};
   let dropped = 0;
   try {
     const goals = Array.isArray(parsed.goals) ? parsed.goals : [];
     parsed.goals = goals.filter((g) => {
       const ok = g && typeof g.goal_id === 'string' && allowed.has(g.goal_id);
       if (!ok) dropped += 1;
       return ok;
     });
   } catch (e) {
     // Заметка дороже оценок: любая ошибка разбора — шлём без ключа goals.
     delete parsed.goals;
     dropped = -1;
   }
   // дальше в ai_write_lesson_note уходит parsed, не model
   ```

   Сообщение специалисту, по одной причине на случай (первая подходящая):
   `studentGoals.length === 0` — «у ребёнка нет активных целей, оценки не
   записаны» (и ветка про неизвестную цель тогда не печатается);
   `dropped < 0` — «оценки не записаны»; `dropped > 0` — «оценки по N
   целям не записаны: модель назвала неизвестную цель»; отдельно, если
   `goalsTotal > studentGoals.length` — «показаны не все цели». Молчать
   нельзя: то, что отброшено до RPC, в `progress_skipped` не попадает.
   Список — только `active` (0048 Р3): цель на паузе воркер отбросит, а
   `ai_write_lesson_note` приняла бы — этот фильтр и есть место, где
   они сходятся.

   **Сохранение данных выполнений у `poll` — выключить** (Settings →
   Save execution data: none / только ошибки). Иначе формулировки целей и
   транскрипт оседают в БД n8n — та же причина, что «аудио не храним».
6. Сообщение специалисту в `chat_id` из ответа — через
   `notification_begin`/`notification_finish`, как и все остальные, с
   `p_subject_id = student_id`.
7. `ai_job_finish` → `{"p_event_id": <id>}`, затем `ack_events`.

**Любая ошибка на шагах 2–5** — `ai_job_fail` с русской причиной, и
**не** `fail_events` напрямую: `ai_job_fail` зовёт его сам и ставит
терминальный статус, иначе следующий проход оплатит Whisper и Claude
заново. Она же кладёт событие `lesson.voice_failed` — его доставка
специалисту идёт обычным путём шага 3 основного сценария (ветка в
`event_messages` — 0047; до неё событие уходило в `skipped`, и специалист
о сбое не узнавал). Утверждение черновика в вебе кладёт
`lesson.note_approved` — резюме родителю уходит тем же путём (0047), в
сценарии для него ничего отдельного нет.

**Порядок узлов — часть инварианта**, ровно как у `notification_begin`
выше. `ai_job_begin` обязан идти **до** платных вызовов, `ai_job_finish`
— после записи. В SQL этот порядок ничем не выражен: `ai_write_lesson_note`
не требует существования строки работы, и pgTAP его не проверит.

**Таймаут сценария** должен быть больше худшей пачки: обработка одного
голосового — 20–60 секунд, а `claim_events` забирает до 100 событий любых
типов. Пять диктовок подряд это 3–5 минут, и порог `release_stale_claims`
(10 минут) оказывается близко. `ai_job_begin` держит окно в 8 минут: пока
прогон свеж, второй обработчик получает отказ.

**Провайдер один — OpenAI, на обе задачи** (решение владельца
20.09.2026). Промт этапа предполагал распознавание у OpenAI и резюме у
Anthropic, но техническая нужда в двух отсутствует: распознавания у
Anthropic нет вовсе, значит «два провайдера» означало бы два ключа, два
счёта и два баланса, каждый из которых кончается молча. Разница в цене на
объёмах центра — единицы центов в месяц. База провайдера не знает: в
`ai_usage.model` лежит просто текст, сменить можно в любой момент правкой
в n8n, без миграции.

**Курс токенов в тыйыны** живёт в переменных n8n и устаревает — база
пишет присланное. Историю спасает то, что в `ai_usage` лежат сами токены,
модель и строка курса: пересчёт возможен, если курс поменялся.

**Про «аудио не храним».** Мы его не сохраняем: файл проходит через n8n и
никуда не кладётся, а `file_id` вычищается из события в `ai_job_finish`.
Но копия остаётся на серверах Telegram и по `file_id` доступна любому, у
кого есть токен бота, — удалить её мы не можем.

## Сценарий `schedule` — раз в час

1. `lesson_reminders` → `{}` — занятия в ближайшие 18 часов.
2. `daily_digest` → `{}` — сводка центрам, у которых местный час ≥ 8.
3. `installments_notify` → `{}` — платежи по рассрочке на сегодня и
   просроченные.
4. `subscription_reminders` → `{}` — центрам с местным часом ≥ 8: срок
   подписки или пробного периода заканчивается через 0–3 дня
   (`subscription.ending`) или уже истёк (`subscription.expired`). Пока у
   центра открыта заявка на оплату — молчит (0052).

Все четыре идемпотентны по построению (отметки в `lesson_reminders_sent`,
`center_digest_runs`, `installments.*_notified_at`,
`subscription_reminders_sent`), поэтому лишний запуск безвреден, а
пропущенный час наверстывается следующим. Четвёртую ноду владелец
добавляет в сценарий по образцу второй (тот же HTTP-запрос, другое имя
функции).

## Сценарий `watchdog` — раз в десять минут

`release_stale_claims` → `{"p_older_than": "10 minutes"}`. Возвращает в
очередь пачки, которые кто-то забрал и не закрыл: n8n перезапустили или
контейнер умер посреди отправки.

## Сценарий `alerts` — по вебхуку

Единый канал ошибок инфраструктуры в Telegram; подробный порядок
настройки — [docs/OBSERVABILITY_SETUP.md](../docs/OBSERVABILITY_SETUP.md),
шаг 5. Здесь — только форма сценария.

1. Нода **Webhook**: `POST`, path `alerts`, ответ `Immediately`. Production
   URL — адрес, который получают Sentry (Alerts → Webhooks) и UptimeRobot
   (alert contact типа Webhook). Он же — **Error workflow** для `poll`,
   `schedule` и `watchdog` (Workflow Settings каждого).
2. Нода **Code**: из тела собрать одну строку —
   `🔴 Sentry: <event.title>\n<url>` для Sentry, иначе
   `⚠️ <source>: <тело, обрезанное до 500 символов>`.
3. Нода **Telegram** → `sendMessage` в приватную группу владельца. Токен —
   тот же `TELEGRAM_BOT_TOKEN`, что уже шлёт родителям: второй бот не
   нужен, группа отдельная. `chat_id` группы — из `getUpdates` после
   первого сообщения в ней.

Ничего в базу этот сценарий не пишет и в PostgREST не ходит — это не
событие продукта, а сигнал дежурному; в `events` его нет намеренно.

## Почему здесь нет JSON-экспорта

Экспорт n8n содержит идентификаторы креденшелов конкретного инстанса и
версии нод — собранный вслепую, он не импортируется, а чинится дольше, чем
собирается руками по этому файлу. Экспорт кладётся сюда после того, как
владелец поднимет инстанс и соберёт сценарии; тогда же в него попадут
реальные id креденшелов, которые в репозиторий не коммитятся.
