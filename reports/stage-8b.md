# Этап 8b — prod-контур

Дата: 2026-09-24 — 2026-09-25
PR: #131 (ADR-010, `deploy-prod.yml`), #142 (ref прод-проекта), #144 (чек-лист
    ADR-010 по шагам, `mint-role-jwt.mjs`, этот отчёт)
Миграции: нет — этап про контур, не про схему

## Что это даёт

У LogoCRM появилась настоящая рабочая среда, отдельная от тестовой. До
этого всё — и тестовые аккаунты, и каждая новая миграция — жило в одной
базе; подключить туда реальный центр с реальными детьми было нельзя.
Теперь есть прод-база (`logocrm-prod`) с полной схемой и защитой входа
(подтверждение email, проверка утёкших паролей, MFA у владельца
платформы), прод-приложение `https://logocrm-prod.vercel.app`, Telegram-бот и
уведомления, которые смотрят в прод. Схема в прод катится только кнопкой
с явным подтверждением и одобрением владельца; код — автоматически при
каждом мерже в `main`. Владелец может зарегистрировать первый центр.

## Отступления от ТЗ

- **Регион Supabase — `ap-south-1` (Мумбаи), не Frankfurt**: проект
  создан владельцем в том же регионе, что staging; регион после создания
  не меняется. Для Бишкека Мумбаи ближе Франкфурта, требования хранить
  данные в ЕС нет — оставлено (ADR-010 п.1).
- **Один Telegram-бот на обе среды** (решение владельца), не второй бот.
  Следствие: входящие команды бота (привязка, `/today`, `/balance`,
  кнопка «приду», голосовые) обслуживает только прод; staging остался с
  исходящими уведомлениями в тестовые чаты.
- **Отложено до первого платящего центра** (одна граница «прод стал
  настоящим»): PITR/бэкапы (нужен Pro-план Supabase — прод пока без
  бэкапов, реальные центры туда подключать нельзя), домен (`logocrm.kg`,
  DNS в Cloudflare, приложение на `app.`), Sentry и UptimeRobot на прод.
- **Два Vercel-проекта** вместо одного с окружениями: ключи баз лежат в
  разных проектах, перепутать staging и прод физически нельзя (открытый
  вопрос промта, решён владельцем).
- Прод-переменные `OPENAI_API_KEY`, `SUPABASE_BOOKING_JWT`,
  `SUPABASE_BOT_JWT` и креденшел n8n заводились из локальных файлов
  владельца: JWT выпускаются `packages/db/scripts/mint-role-jwt.mjs` с
  секретом подписи прод-проекта на машине владельца, значения в чат и в
  репозиторий не попадали, файлы удалены после загрузки.

## Найденные дефекты

- **Кнопки GitHub в настройках окружения**: секрет был создан как
  отдельное окружение с именем `SUPABASE_ACCESS_TOKEN`, а required
  reviewer у `Production` не сохранился — первый деплой стартовал без
  одобрения и упал на «Нет SUPABASE_ACCESS_TOKEN», ничего не применив.
  Урок в ADR-010: «Add environment secret» живёт внизу страницы, «Save
  protection rules» — отдельная кнопка своего блока.
- **Vercel не отдаёт значения секретов даже своему токену**: попытка
  перенести `OPENAI_API_KEY` из staging через API положила в прод
  зашифрованную заглушку. Переменная удалена и заведена заново из файла
  владельца. Правило: секреты между проектами Vercel не копируются —
  только вводятся заново.
- **Токен Vercel CLI на машине истёк 31.08** — вход обновлён
  (`pnpm dlx vercel login`; `npx`-кэш пакета `vercel` был повреждён).
- **Классификатор Claude Code** блокирует агенту всё, что похоже на
  прод-деплой, включая чтение вкладки терминала: скрипты создания
  Vercel-проекта запускались из терминала владельца, результат
  проверялся GET-запросами к API.
- Заметок на `stages.md` этап 8 стоял ⬜, хотя 8a закрыта 24.09 — поправлено
  этим отчётом.

## Что осталось владельцу

- **Живая приёмка**: зарегистрировать свой центр на
  `https://logocrm-prod.vercel.app`, подтвердить email по письму (это
  проверит Site URL из ADR-010 п.4 — письмо должно вести на
  `logocrm-prod.vercel.app`, не на `localhost`), завести специалиста и
  ученика, привязать Telegram через `/app/telegram`, отправить боту
  `/today`. После этого агент сверяет `events`/`notification_log` в
  прод-базе через MCP.
- До первого платящего центра: PITR (Pro-план Supabase), домен, Sentry
  (`NEXT_PUBLIC_SENTRY_DSN`, `SENTRY_AUTH_TOKEN` в `logocrm-prod`),
  UptimeRobot на `https://logocrm-prod.vercel.app/api/health`.
- Отозвать ключ API n8n `claude-prod-setup` — он больше не нужен.
- Порядок выката несовместимых миграций: сначала «Deploy production»
  (схема), потом мерж кода — прод-приложение собирается при каждом мерже
  в `main`, а схема только кнопкой (ADR-010 п.4).
