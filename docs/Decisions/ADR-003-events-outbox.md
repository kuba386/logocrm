# ADR-003. События через transactional outbox

Дата: 2026-09-07
Статус: принято

## Контекст

Действия в CRM тянут за собой побочные эффекты: списание занятия с абонемента →
уведомление родителю; создание центра → приветственное письмо; пропуск занятия →
пересчёт долга. Часть эффектов уходит во внешние сервисы (WhatsApp, email), и
они падают.

Если отправлять уведомление прямо в обработчике запроса:

- падение внешнего сервиса откатывает или ломает бизнес-операцию;
- при ретрае запроса уведомление уходит дважды;
- нет истории «что вообще произошло в системе».

Брокер (RabbitMQ, Kafka) — отдельная инфраструктура, которую в MVP на две
машины никто не хочет администрировать. Кроме того, запись в брокер не входит
в транзакцию Postgres: возможна ситуация «событие отправлено, транзакция
откатилась».

## Решение

Transactional outbox: таблица `events` в той же базе и той же транзакции.

```sql
create table events (
  id bigserial primary key,
  center_id uuid not null,
  type text not null,
  payload jsonb not null,
  created_at timestamptz default now(),
  processed_at timestamptz
);

create index events_unprocessed_idx on events (processed_at) where processed_at is null;
```

Запись — только через `emit_event(type, payload)`. Чтение — воркером по
`processed_at is null`, с проставлением `processed_at` после успешной обработки.

Типы событий описаны в `packages/contracts/src/events.ts` как zod-схемы и
собраны в `discriminatedUnion` → тип `AppEvent`. SQL пишет payload, TypeScript
его валидирует на входе воркера.

Имя события — `сущность.действие` в прошедшем времени: `center.created`,
`membership.created`. Событие — свершившийся факт, не команда.

## Последствия

Хорошо:

- событие и бизнес-операция коммитятся атомарно: не бывает события без факта
  и факта без события;
- при падении воркера ничего не теряется — необработанные строки на месте;
- `events` бесплатно даёт журнал: «что произошло в центре за месяц»;
- ноль новой инфраструктуры.

Плохо:

- доставка «не раньше чем», а не мгновенная: задержка равна интервалу воркера;
- гарантия **at-least-once** — обработчики обязаны быть идемпотентными;
- таблица растёт; обработанные события старше 90 дней архивируются отдельной
  задачей (пока не реализовано);
- при нескольких воркерах нужен `select ... for update skip locked` — сейчас
  воркер один.

`parseAppEvent()` намеренно возвращает результат, а не бросает исключение:
неизвестный тип события (старый воркер, новая схема) должен приводить к пропуску
строки, а не к падению всей очереди.
