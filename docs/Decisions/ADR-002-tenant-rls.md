# ADR-002. Изоляция тенантов через RLS и center_id в JWT

Дата: 2026-09-07
Статус: принято

## Контекст

Один инстанс обслуживает много логопедических центров. В базе — персональные
данные детей: диагнозы, записи занятий, контакты родителей. Утечка данных между
центрами — не баг, а инцидент с юридическими последствиями.

Варианты:

1. **База на центр (schema-per-tenant).** Идеальная изоляция, но миграции нужно
   прогонять по N схемам, а Supabase Auth и PostgREST на это не рассчитаны.
2. **Фильтр `where center_id = ...` в коде приложения.** Один забытый `where` —
   и данные чужого центра в выдаче. Проверять это на code review бесконечно.
3. **`center_id` + RLS в Postgres.** Фильтр не в коде, а в базе; забыть его
   физически невозможно.

## Решение

Вариант 3. Каждая таблица с данными центра имеет `center_id not null` и
RLS-политику, накладываемую процедурой `apply_tenant_rls(tbl)`.

Активный центр берётся **только** из JWT:

```sql
create function current_center() returns uuid as $$
  select nullif(auth.jwt() -> 'app_metadata' ->> 'center_id', '')::uuid;
$$;
```

`app_metadata` подписывается GoTrue и не редактируется пользователем (в отличие
от `user_metadata`). Значение туда пишет `switch_center(uuid)` — `security
definer`-функция, которая сначала проверяет наличие membership.

`center_id` не передаётся в теле запроса и не хранится в куке приложения: и то,
и другое клиент контролирует, а значит подделает.

## Последствия

Хорошо:

- изоляция обеспечивается базой, а не дисциплиной разработчика;
- нарушение проверяется тестом (`packages/db/supabase/tests/`), а не глазами;
- multi-center пользователи (логопед работает в двух центрах) поддержаны из
  коробки: несколько строк в `memberships`.

Плохо и что с этим делать:

- **JWT кэширует `center_id` до истечения токена.** После `switch_center`
  обязателен `supabase.auth.refreshSession()`. Забыть это — самая вероятная
  ошибка в проекте; поэтому вызов зашит в server actions онбординга и выбора
  центра, а не оставлен на усмотрение вызывающего кода.
- Отзыв доступа не мгновенный: до истечения токена (1 час) пользователь может
  ходить в центр с уже удалённым membership. Для критичных операций проверяем
  `my_role()` дополнительно — она читает таблицу, а не токен. Именно поэтому
  `app/app/layout.tsx` дергает `rpc my_role()`, а не доверяет JWT.
- Политики надо помнить: новая таблица без `apply_tenant_rls` останется без
  RLS и станет видна всем. Это ловится пунктом чеклиста в `docs/Database.md`
  и обязательным pgTAP-тестом на изоляцию.
- Роли `teacher` и `parent` не покрываются общим шаблоном — у них доступ по
  цепочке связей. Их политики пишутся вручную на каждой таблице.

## Не только RLS: гранты на функции

RLS защищает таблицы. Функции она не защищает — у них своя система прав, и
Supabase здесь работает против нас двумя способами сразу:

1. Postgres выдаёт `EXECUTE` роли `PUBLIC` на каждую новую функцию;
2. Supabase дополнительно выдаёт `EXECUTE` ролям `anon` и `authenticated`
   через default privileges на схему `public`.

Поэтому `revoke ... from public` недостаточно (остаётся явный грант `anon`),
и `revoke ... from anon` тоже недостаточно (остаётся `PUBLIC`). Нужны оба —
это сделано в миграциях 0002 и 0003.

Практическое следствие: `security definer`-функция в схеме `public` по
умолчанию торчит наружу как `/rest/v1/rpc/<имя>` и вызывается **без
авторизации**. Первая версия `emit_event` принимала `p_center_id` и не
проверяла ничего — то есть любой человек в интернете мог писать события в
outbox любого центра, а пользователь центра А — в центр Б. RLS на `events`
это не ловила: запись шла в обход, изнутри definer-функции.

Отсюда два правила для всех будущих RPC:

- каждая `security definer`-функция начинается с проверки `auth.uid() is not
  null` и проверки прав на конкретный `center_id` (`role_in(...)`);
- после каждой миграции запускается линтер Supabase (`get_advisors`, вкладка
  Advisors в дашборде). Локальные pgTAP-тесты эту категорию ошибок не видят:
  они ходят от роли `authenticated`, а не от `anon`, и не проверяют гранты.
