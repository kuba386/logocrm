# ADR-010. Чек-лист prod-контура (этап 8b)

Дата: 2026-09-24
Статус: принято, выполнение — по чек-листу ниже

## Контекст

Этап 8a закрыт (`reports/stage-8.md`): продукт можно продавать — тарифы,
лимиты, trial и read-only, заявки на оплату, воронка, экспорт и удаление
центра, публичная запись. Всё это работает против единственного сейчас
Supabase-проекта `logocrm` (ref `hiwstqrnxrlfuanvfggq`, регион `ap-south-1`)
— того же, что видит владелец в staging, с тестовыми пользователями,
seed-данными и выключенным подтверждением email (ADR-004).

Этап 8b — не код продукта, а отдельный контур: второй Supabase-проект,
отдельный деплой по кнопке с подтверждением, отдельный Vercel-таргет,
наблюдаемость на реальных данных. Ни один пункт не проверяется pgTAP или
Playwright — только живым прогоном на самом проде, и почти каждый пункт
требует рук владельца (аккаунты, дашборды, секреты — CLAUDE.md).

`docs/OBSERVABILITY_SETUP.md` (0057, PR #129) уже закрыл Sentry/
UptimeRobot/n8n-алерты и лимиты расходов — но настроено на **staging**-
проекте `logocrm`, как черновой прогон перед прод-контуром. Для прода эти
шаги повторяются на новом проекте (Sentry — тем же проектом с тегом
`environment=production`, не вторым проектом: одна панель ошибок на обе
среды, разделённые окружением, — Sentry поддерживает это из коробки).

## Решение

Чек-лист — ниже, по разделам промта этапа 8 (`docs/Roadmap/stages.md`) и
ADR-004. Пункты, которые уже можно закрыть в коде без прод-секретов,
закрыты этим же ADR (см. «Что уже в репозитории»); остальное —
**исключительно руками владельца**, агент не имеет доступа ни к одному
из перечисленных дашбордов.

### 1. Supabase — новый проект

- [x] Создать проект `logocrm-prod` — **создан владельцем 24.09.2026**,
      ref `vlsnfuhmozkywbovkazc`, регион **`ap-south-1` (Мумбаи)**, Postgres
      17. Планировался Frankfurt (`eu-central-1`); регион после создания не
      меняется, и решение оставить `ap-south-1` записано здесь: для
      Бишкека Мумбаи географически ближе Франкфурта, staging в том же
      регионе, требования хранить данные в ЕС нет. Отдельно от staging и по
      данным, и по биллингу.
- [x] **Без seed** — `packages/db/supabase/seed.sql` на прод не
      применяется никогда: там тестовые пользователи и фикстуры.
      `deploy-prod.yml` seed не трогает (`db push`), первый деплой
      25.09.2026 прошёл без него — проверено списком миграций через MCP.
- [x] **Confirm email: ON** — включено владельцем 25.09.2026 (ADR-004 — на
      staging выключено намеренно, на проде обязательно: доступ к
      персональным данным детей).
- [x] **Leaked Password Protection: ON** — включено владельцем 25.09.2026.
- [x] **MFA для owner-аккаунта** платформы в самом Supabase — включено
      владельцем 25.09.2026 (не путать с MFA внутри LogoCRM — в продукте
      его нет и не планируется в 8b).
- [ ] **PITR (Point-in-Time Recovery) / бэкапы** — **отложено владельцем
      25.09.2026**: проект на Free-плане, бэкапов нет. Прод без бэкапов —
      это вторая тестовая база; включить (перевод проекта на Pro) до
      первого платящего центра, и до этого не подключать реальные центры
      с данными детей.
- [x] Применить миграции с нуля — **сделано 25.09.2026** первым запуском
      `deploy-prod.yml` (владелец нажал, одобрил как required reviewer):
      в проде 0001–0065, история совпадает с каталогом. Советник
      безопасности Supabase на проде — тот же набор известных
      предупреждений, что на staging (definer-функции с грантом
      `authenticated`, `rls_enabled_no_policy` на служебных таблицах),
      без `auth_leaked_password_protection` — переключатель шага 1
      подтверждён. **Не** копированием данных из staging: это разные
      центры, разные пользователи, копировать нечего и незачем — тот же
      принцип, по которому данные старого MVP в LogoCRM не переносились
      вовсе (решение владельца 9.09.2026).
      Первый запуск (19:22 UTC 24.09) упал на «Нет SUPABASE_ACCESS_TOKEN»,
      ничего не применив: секрет был заведён как отдельное окружение с
      именем `SUPABASE_ACCESS_TOKEN`, а required reviewer у `Production`
      не сохранился. Урок для чек-листа: кнопка «Add environment secret»
      живёт внизу страницы окружения, «Save protection rules» — отдельная
      кнопка своего блока.
- [x] Записано: ref `vlsnfuhmozkywbovkazc`, пулер
      `aws-0-ap-south-1.pooler.supabase.com` — оба вписаны в
      `deploy-prod.yml` (PR после создания проекта), placeholder снят.

### 3. `deploy-prod.yml`

**В репозитории** — `.github/workflows/deploy-prod.yml`. Только
`workflow_dispatch`, требует явного текстового подтверждения (input
`confirm` = `DEPLOY PRODUCTION`) и запуска только с `main`.
`environment: production` — сам факт запуска уходит на подтверждение
required reviewer (пункт 2). Ref прод-проекта зашит в файл (PR #142,
24.09.2026) и меняется только через ревью кода — не секретом.
**Работает: первый прогон 25.09.2026 зелёный** (пункт 1).

### 4. Vercel

- [x] **Два Vercel-проекта** — решение владельца 25.09.2026: `logocrm-web`
      остаётся staging, прод — новый `logocrm-prod`
      (`prj_C7jjboL0Qw8xP3Jokvurr9EUJAUZ`, команда `kuban1`), создан
      агентом через Vercel API как копия staging-проекта: корень
      `apps/web`, Next.js, Node 24, репозиторий `kuba386/logocrm`,
      production-ветка `main`. Довод за два проекта: ключи баз лежат в
      разных проектах — перепутать staging и прод физически нельзя.
      Каждый push в `main` теперь собирает **оба** проекта; схема при
      этом уезжает только в staging (`deploy-prod.yml` — по кнопке), так
      что прод-приложение может опередить прод-схему на одну миграцию —
      порядок выката: сначала «Deploy production» (миграции), потом
      мерж/деплой кода, если миграция несовместима со старым кодом.
- [ ] Домен — **отложено владельцем 25.09.2026** вместе с PITR: до
      первого платящего центра прод живёт на `logocrm-prod.vercel.app`;
      покупка домена (`logocrm.kg` у местного регистратора, DNS в
      Cloudflare, приложение на `app.`-поддомене) — в день появления
      первого реального центра.
- [x] Переменные окружения prod — заведены агентом через API 25.09.2026:
      `NEXT_PUBLIC_SUPABASE_URL` = `https://vlsnfuhmozkywbovkazc.supabase.co`,
      `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (публичный ключ прод-проекта),
      `NEXT_PUBLIC_SITE_URL` = `https://logocrm-prod.vercel.app`,
      `OPENAI_API_KEY` — **заводит владелец руками**: попытка перенести
      из staging через API дала зашифрованное значение (Vercel не отдаёт
      секреты даже своему токену), переменная удалена, чтобы ассистент на
      проде не бил в OpenAI мусорным ключом. `NEXT_PUBLIC_TELEGRAM_BOT` —
      имя бота, то же, что на staging (решение «тот же бот», пункт 6).
- [ ] Supabase Auth прод-проекта → URL Configuration: **Site URL** =
      `https://logocrm-prod.vercel.app`, **Redirect URLs** =
      `https://logocrm-prod.vercel.app/**` — без этого письма
      подтверждения email и ссылки восстановления ведут на дефолтный
      `localhost:3000`. Руками владельца (дашборд).
- [x] `SUPABASE_BOOKING_JWT` (0057, `public_booking`) — выпущен владельцем
      25.09.2026 локально (`SUPABASE_JWT_SECRET='…' node
      packages/db/scripts/mint-role-jwt.mjs public_booking`, секрет

      sensitive-переменная через API, локальный файл удалён; прод

## Последствия

Пока хотя бы один пункт раздела 1–2 не закрыт, `deploy-prod.yml` физически
не запустится на реальный прод (ref не пройдёт проверку, а без секрета в
`production` шаг подключения откажет с понятным текстом — тот же приём,
что уже есть в `deploy-staging.yml`). Значит нет риска, что случайный
`workflow_dispatch` до готовности прод-проекта что-то испортит.

Чек-лист приёмки этапа 8 (`docs/Roadmap/stages.md`, пункт 6) — «регистрация
реального центра → приглашение специалиста → урок → посещение → SOAP из
голосового. Sentry ловит тестовую ошибку» — выполняется только после
всех пунктов выше, живым прогоном на самом проде.
