# Матрица прав

Кто что видит и может. Источник — код: RLS-политики миграций и гейты в
`security definer`-функциях, а не замысел.

Пополняется по этапам — см. Definition of Done в
[Roadmap/stages.md](Roadmap/stages.md). Сейчас заполнены **этапы 0–2**;
расписание, абонементы и финансы (этапы 3–5) добавляются строками своих
этапов. Почему правило именно такое — в [BUSINESS_RULES.md](BUSINESS_RULES.md).

## Как читать

| Знак | Значение |
|---|---|
| **В** | видит |
| **С** | создаёт |
| **П** | правит |
| **У** | удаляет — в этом проекте почти всегда «архивирует» (`deleted_at`). Настоящий `delete` есть ровно в одном месте: отзыв членства |
| **—** | нет доступа: не «кнопки нет», а база не отдаёт строк |
| _курсив_ | **план этапа 5**, в схеме этого ещё нет |

**`registrar` и `finance` — курсивом целиком.** В базе их нет:
`memberships.role` ограничен `check in ('owner','admin','teacher','parent')`
(`0001_foundation.sql:60`). Колонки заполнены как требование к этапу 5, чтобы
права проектировались заранее, а не доставались после. Что именно придётся
тронуть при их появлении — в [Roadmap/stages.md](Roadmap/stages.md),
доработка этапа 5.

Разница между `owner` и `admin` мельче, чем кажется: она есть только в
настройках центра и в управлении персоналом. Во всём остальном — одно и то
же право.

## Чего в матрице пока нет

Строки этапов 3–5 не заполнены, хотя код этих этапов уже в `main`:
расписание и занятия, посещения и абонементы, платежи, рассрочки, расходы,
ставки и зарплата. Они добавляются сюда по правилу Definition of Done —
вместе с ближайшей правкой соответствующего этапа, чтобы заполнение шло по
коду, а не по памяти.

Известные ориентиры для них, подтверждённые кодом: специалист не видит
`subscriptions` вовсе и получает остаток словом, а не числом; родитель видит
остаток числом по своим детям (`student_balance`); занятия правит только
владелец или администратор, а отметить посещение специалист может лишь на
своём занятии (`mark_attendance`, `teacher_of_lesson`).
