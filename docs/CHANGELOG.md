### Добавлено

- **Бот: посещение кнопками и заметка текстом для специалиста** —
  `0071_bot_teacher_actions.sql` + `apps/tg-bot` (решение владельца
  26.09.2026: работать с телефона там, где действие — кнопка или одно
  сообщение; ДЗ и напоминания отклонены). Под каждым занятием в `/today`
  — «Отметить» (статусы центра) и «Заметка» (ForceReply → черновик
  `lesson_notes`, `soap.objective`); на групповом занятии — сначала
  ребёнок. Контекст «чат ждёт следующего шага» — `bot_pending_actions`
  (один живой на чат, TTL 15/3 мин, кнопка несёт один uuid). Первый раунд
  ревью нашёл, что план не работал бы вовсе: AFTER-триггер посещения зовёт
  `emit_event` с гейтом `auth.uid()`, и из контура `bot_worker` любая
  отметка падала бы 42501 — заведён `emit_event_internal` без грантов,
  триггеры `attendance_recalc_trigger`/`check_absent_streak` переизданы
  дословно с 0010. Путь бота даёт те же события, что экран (pgTAP держит
  `attendance.marked`, `no_subscription`, `low_balance`). Заметка — с явным
  `created_by`, чтобы автор мог утвердить её с экрана (0041 Р2); остаётся
  черновиком до резюме родителю (0047 Р3). Бот не переписывает
  существующую отметку (другой статус — отказ «на экране»: автора смены
  денег в контуре бота не фиксирует ничто), права и read-only
  перепроверяются на каждом шаге, занятие — только сегодняшнее в поясе
  центра (кнопка в переписке живёт дольше занятия, 0035 Р7).
  `bot_today` переиздана: `starts_local` — время в поясе центра из SQL
  (бот форматировал сырой timestamptz как UTC — Бишкек видел 09:00 вместо
  15:00), `can_mark`/`can_note`. Второй раунд ревью (написанный SQL)
  закрыл ещё четыре: «ждём диктовку» — весь цикл до черновика ИИ, не «до
  прихода файла» (иначе печатный текст молча съедал оплаченный SOAP);
  чужой черновик из бота не дописывается; ответ на устаревший
  ForceReply-промпт отвергается по `message_id`; `bot_pending_actions` —
  в deny-list экспорта. Деплой бота на Railway — руками владельца.
- **Чтение-письмо — пятый, последний раздел речевой карты** —
  `0068_reading_writing_assessments.sql` (Фаза 3.5, по одному разделу за
  раз). ИСТОРИЯ, сочетает скалярные категориальные поля (как просодика,
  0067) и два независимых `text[]` (как слоговая структура, 0066) — самый
  сложный из пяти разделов. `reading_method` — описательная шкала без
  оси нормы (сознательно выведена из контракта «единый `normal`», pgTAP
  держит границу забором на текст CHECK). `writing_quality` — новая ось
  нормы для письма, добавленная во втором раунде ревью: без неё пустой
  `writing_errors` был бы неотличим от «не оценивалось». Именованный CHECK
  запрещает `writing_quality='normal'` вместе с непустым `writing_errors`
  — второй проход ревью нашёл, что полный-снимок форма могла сохранить
  оба разом. Инвариант «хотя бы одно поле» — раздельная формула для
  скаляров (`num_nonnulls`) и массивов (`coalesce(cardinality(...),0)>0`):
  `num_nonnulls()` молча принимает массивы и считал бы `'{}'` за non-null,
  что сделало бы констрейнт всегда истинным. Проверка архивного
  специалиста и `student_alive` в `update_` для всех ролей — по образцу
  0067 (обе находки второго раунда ревью 0067 закрыты здесь с самого
  начала).
- **Просодика — четвёртый раздел речевой карты** —
  `0067_prosody_assessments.sql` (Фаза 3.4, по одному разделу за раз).
  ИСТОРИЯ, как слоговая структура (0066), но форма колонок — как
  артикуляционный аппарат (0065): шесть категориальных `text`-полей
  (темп, ритм, интонация, дыхание, голос, логическое ударение) с CHECK на
  закрытый список кодов, не массивы. Единый код нормы `'normal'` во всех
  шести полях; `NULL` — «не оценивалось», не «в норме» (та же цена
  ошибки, что `student_balance.lessons_left`). Инвариант «хотя бы одно
  содержательное поле» — именованный CHECK на таблице
  (`prosody_assessments_not_empty`), не только проверка в `record_`: форма
  правки — полный снимок и могла обойти RPC-guard. Сентинел `''`/пробел →
  `null` на обеих функциях для всех семи текстовых полей. `student_alive`
  в `update_` — общее предусловие для всех ролей, включая owner/admin, не
  только ветки teacher (симметрия с restrictive-политикой на чтение).
  Специалист — не архивный, проверка одна после ветвления teacher/owner-
  admin. Составной FK на `teachers` — `on delete set null (teacher_id)` со
  списком колонок (0022), не голый `on delete set null` (долг 0036/0066).
  Все находки — со второго прохода ревью написанного SQL, до CI.
- **Слоговая структура — третий раздел речевой карты** —
  `0066_syllable_assessments.sql` (Фаза 3.3, по одному разделу за раз).
  В отличие от анамнеза (0063) и артикуляционного аппарата (0065) —
  ИСТОРИЯ, не профиль (решение владельца): новая запись на каждое
  обследование, архивация вместо правки на месте, как `diagnostics`.
  `affected_classes` (14 классов слоговой структуры по А.К. Марковой) и
  `error_types` — два независимых `text[]` без привязки ошибки к
  конкретному классу (решение владельца — проще и быстрее для первой
  версии). Дедуп и сортировка (числовая для классов, не лексикографическая
  — иначе `'10'` встаёт раньше `'2'`) перед каждой записью в `record_`/
  `update_`; `record_` требует хотя бы одно содержательное поле — иначе
  пустой вызов читался бы как «обследован, нарушений нет»; `conclusion`
  получил сентинел `''`/`null` (0059 Р16). Restrictive-политика —
  `student_alive` для всех, включая owner/admin (без исключения — план
  сперва его закладывал, но ревью написанного SQL нашло, что рассуждение
  опиралось на несуществующий сегодня сценарий, и убрало настоящий слой
  защиты без пользы). Гранты — только `select`, запись строго через RPC.
- **Артикуляционный аппарат — второй раздел речевой карты** —
  `0065_student_articulation.sql` (Фаза 3.2, по одному разделу за раз).
  Строение/подвижность губ, зубов, прикуса, нёба, языка, уздечки —
  фиксированные клинические находки. Значения — латинские коды (не
  русский текст в колонке), CHECK именованы явно, русские тексты — в
  `errors.ts`; RPC не дублирует список кодов (только форма значения,
  допустимость — исключительно CHECK). Четыре поля, где находки
  сочетаются, — `text[]`. Круг доступа — `clinical_teacher_sees` или
  назначенный `primary_teacher_id`, симметрично чтению и записи (не только
  первому заполнению — асимметричный вариант воспроизводил тупик 0063
  Р10). Сравнение авторства — только через `coalesce(..., false)`:
  голое `created_by = auth.uid()` при `NULL` пропускало проверку прав
  молча (найдено вторым проходом ревью).
- **AI-ассистент администратора `/app/assistant`** — `0064_assistant.sql`
  (Backlog, владелец 11.09.2026; решения владельца 24.09.2026). Вопрос
  обычным языком — «какие занятия завтра», «кто должен денег», «у кого
  заканчивается абонемент», «сколько пришло за неделю», «найди Айжан».
  Провайдеру (OpenAI, ADR-009) уходит **только текст вопроса и
  сегодняшняя дата в поясе центра**: модель разбирает вопрос в намерение с
  параметрами (function calling), а ответ собирает база под правами
  спросившего — те же таблицы под RLS и те же RPC, что у экранов; имена
  детей и деньги провайдер не видит (Vitest держит тело запроса). Карта
  «намерение × роль» — в SQL (`assistant_intents_for`): из неё собирается
  список инструментов для модели и повторно проверяется намерение при
  закрытии попытки — бухгалтеру «занятия» не предлагаются, а не
  показываются пустыми. Попытка (`assistant_requests`: актор, намерение,
  статус) и расход (`ai_usage`, `kind = 'question'`, цена по ставке из
  SQL — `ai_model_rates()`, не параметром) — разные сущности; квота —
  тарифный лимит `plans.limits.ai_questions_month` (trial 300, Solo 100,
  Studio 500, Center 2000) = оплаченные вопросы месяца + попытки в полёте
  ≤ 5 мин под advisory lock; отказ с текстом тарифа — как у голосовых.
  Неоплаченный центр — `PT402` в горловине. Один вопрос = ровно один вызов
  провайдера. Всем сотрудникам, родителю — нет. Требует владельца:
  `OPENAI_API_KEY` в Vercel — без него страница говорит «не настроен».
- **Анамнез — первый раздел речевой карты** — `0063_student_anamnesis.sql`
  + `anamnesis-panel.tsx` (Фаза 3.1, владелец 24.09.2026: карта строится по
  одному разделу за раз). `student_anamnesis` — профиль, не история: одна
  строка на ребёнка, беременность/роды, ранние вехи развития и речи,
  заболевания, наследственность, условия воспитания, слух/зрение. Запись —
  единственный RPC `set_student_anamnesis` с jsonb-патчем и белым списком
  ключей вместо растущей позиционной сигнатуры; оптимистичная блокировка
  по `updated_at`. Видимость — новая `clinical_student_visible`, единая
  для всего клинического блока (`clinical_diagnostic_visible` из 0059
  теперь её обёртка); родителю не видна ни в каком виде (ADR-005). Первое
  заполнение доступно любому специалисту центра (анамнез чаще собирают до
  первого занятия), автор сохраняет доступ к своей записи и дальше — но
  это исключение не должно обходить проверку «ученик жив» (поймал только
  CI: `created_by = auth.uid()` в политике обязан идти через отдельную
  `student_alive(uuid)`, а не через inline `exists()`, который сам упирался
  бы в RLS `students`).
- **Глобальный поиск** — `0062_global_search.sql` (Backlog, владелец
  11.09.2026). Одно поле в сайдбаре (и строкой под мобильным хедером):
  имя или телефон → ученик, плательщик, ближайшее (или идущее сейчас)
  занятие; `/` фокусирует, стрелки и Enter — навигация. Порядок задаёт
  база одним ключом `rank` (телефон → префикс → вхождение, архивные —
  после). Карточка плательщика `/app/payers/[id]` теперь гейтится RLS, а
  не ролью в коде — иначе регистратор и родитель получали бы из поиска
  строки, которые нельзя открыть. Главный
  вопрос владельца — «поиск не должен показать роли то, чего ей не видно
  в списках» — решён не вторым набором предикатов, а `SECURITY INVOKER`:
  `global_search(p_query, p_limit)` читает таблицы под RLS вызывающего,
  границы выдачи совпадают с политиками по построению (pgTAP держит
  `prosecdef = false`). Имя плательщика — через `payer_display_name()`,
  как в `students_teacher_view`: специалист находит «маму Гульнару» там,
  где видит её в списке, и не получает телефон. Телефон — в любом
  формате: полный через `normalize_kg_phone`, частичный (≥ 4 цифр) как
  вхождение в местные 9 цифр, `phone_alt` тоже. `ё`/`е` и регистр не
  важны. Бухгалтеру поле не показывается: у роли нет политик на
  `students`/`payers` (0031), её списки рисуют definer-RPC — под invoker
  поиск ей пуст, и это записано, а не «починено» definer-ом. Ближайшее
  занятие берётся от уже найденных учеников по индексу
  `lesson_participants_student_idx` (RLS-квалы не считаются на всей
  таблице занятий), якорится на `lessons` (`lesson_participants` — только
  связка с `deleted_at is null`); неделя для ссылки на расписание
  считается в SQL в поясе центра. Показывается только ответ на последний
  запрос — ответ на «Айж» не перекроет ответ на «Айжан».
- **Подсказка заключения из шкал speech_areas** — `0061_conclusion_suggestion.sql`
  (фаза 2 из 0059, порог владельца 24.09.2026: «нарушено» — значение ≤ 2 на
  шкале 1–5). Чистая функция `suggest_speech_conclusion(jsonb)` — без своей
  таблицы, вычисляется на чтении; первый план с денормализованной
  таблицей-кешом и AFTER-триггером архитектор развернул (каст `jsonb` в
  триггере ронял бы сохранение диагностики на кривых данных, кеш протухал
  бы без бэкфилла). Уровень ОНР не угадывается — общий флаг
  `onr_suspected`, не `onr_1..onr_4`: у функции нет возраста ребёнка на
  входе, чтобы отличить ОНР I от ЗРР (код `zrr`), а уровень из среднего
  трёх шкал путал бы тяжесть местами. `norm` тоже не предлагается никогда
  (ревью написанного SQL): функция не видит карту звуков той же формы,
  пять шкал в норме при искажённых звуках дали бы ложную кнопку «Речь в
  норме». `packages/core/src/nosology.ts` — TS-зеркало для мгновенной
  подсказки в форме; в `diagnostics-panel.tsx` подсказка никогда не
  подставляется в поле сама — только кнопка «Применить».
- **Приглашение родителя — только с карточкой плательщика** —
  `0060_parent_invitation_payer.sql` (Backlog, находка владельца
  18.09.2026). Корень был глубже «телефон не заполнили»: `create_invitation`
  вообще не заполняла `invitations.payer_id`, каждый приглашённый родитель
  приходил «ничьим». Теперь: в форме приглашения для роли «Родитель» —
  выбор карточки из списка (с именами детей) или «новая карточка» по ФИО и
  телефону с прямым предупреждением, что детей к ней ещё надо привязать;
  телефон уже существующей карточки — отказ «выберите из списка», не
  дубль. CHECK `invitations_parent_payer_check` (`NOT VALID` — история
  остаётся) закрывает путь мимо функций, `change_member_role` больше не
  переводит В роль родителя, `accept_invitation` отказывает по карточке,
  архивированной после выдачи ссылки. `link_parent_payer(user, payer|null)`
  и кнопка «Привязать плательщика» в «Сотрудниках» чинят уже существующих
  «ничьих» родителей (раньше — запросом в базу); событие
  `membership.payer_linked` с `previous_payer_id`. Ссылка родителя живёт
  3 дня — она открывает записи семьи. Кабинет родителя различает три
  «пусто»: аккаунт без карточки, карточка недоступна, карточка без детей.
  Висящие parent-приглашения без карточки протушены — перевыпустить с
  плательщиком. Форма сотрудников переведена на общий разбор ошибок
  (`lib/errors.ts`).

- **Выгрузка отчётов в CSV `/app/reports`** — `0058_report_exports.sql`.
  Четыре отчёта пятью функциями: `export_payments(from, to)`,
  `export_salary_summary(month)`, `export_salary_details(month)`,
  `export_attendance(from, to)`, `export_debts()`. Деньги — `can_finance()`
  (owner/admin/finance), посещаемость — только owner/admin (0031: finance
  не видит отметок); отказ — `42501`, не пустой файл. Период — по поясу
  центра, полуоткрытые границы, не больше года (`22023`). Зарплата —
  из одного источника: утверждённый месяц отдаёт снимок `salary_runs.lines`
  (сводка и детализация не расходятся после смены ставки задним числом),
  неутверждённый — `calc_salary`, колонка `approved` говорит, что именно
  выгружено. Долги — двумя колонками (`lessons_debt_tiyin` из
  `student_debts()` и `subscriptions_unpaid_tiyin` = `price − paid` по
  живым абонементам), без сложения. Каждая выгрузка — событие
  `report.exported` с актором, ролью и числом строк (решение владельца:
  след в журнале, без Telegram). CSV собирает сервер (`packages/core/csv.ts`:
  `;`, CRLF, BOM для Excel, формульные значения экранируются `'`), браузер

  получил белый список (`notification_event_types` + FK) вместо трёх копий
  проверки в разных местах.
- `apps/web/app/app/schedule/page.tsx` — ученики и группы запрашивались только
  для owner и admin. Специалист и родитель видели карточку занятия без имени
  ребёнка: «11:00 Занятие». Запрос сделан безусловным, границы держит RLS —
  `students_teacher_read_own` отдаёт специалисту его учеников,
  `students_parent_read_own` родителю его детей.
- `apps/web/app/app/schedule/lesson-panel.tsx` — селект замены имел `id`,
  совпадающий с селектом «Специалист» в диалоге создания. Дубль `id` на одной
  странице ломает связь подписи с полем: туда уходит и скринридер, и
  автотест. Переименован в `substituteTeacherId`, `name` сохранён.

### Конвейер

- **Деплой умеет подключаться по `SUPABASE_ACCESS_TOKEN`** через `--project-ref`
  — CLI получает временную роль через API, пароль базы не нужен. Причина:
  открытый [supabase/supabase#44210](https://github.com/supabase/supabase/issues/44210),
  пулер стабильно отвергает пароль роли `postgres` после сброса в дашборде.
  Четыре попытки с паролем упёрлись в него. Токен аккаунтный, поэтому ref
  зашит в workflow. Пароль остаётся вторым путём на будущее.
  Первый зелёный проход конвейера от коммита до базы — 10 сентября 2026.
  По дороге две ловушки: `--project-ref` без состояния `link` идёт на прямой
  хост (IPv6-only), а сам `supabase link` требует роли Owner/Admin ради ключей
  API. CI пишет `.temp/project-ref` и `.temp/pooler-url` сам — ни один не
  секрет — и `link` не вызывает.
- Деплой в staging стал переиспользуемым workflow, а CI вызывает его джобом
  с `needs: [db]`. Гарантия «деплой не может опередить pgTAP» теперь держится
  зависимостью между джобами. Раньше деплой гейтился успехом всего прогона
  CI — после появления приёмочных тестов красный Playwright останавливал бы
  выкладку корректной схемы.
- `cancel-in-progress` отключён на `main`: деплой переехал внутрь прогона CI,
  и второй пуш подряд убил бы `supabase db push` посреди применения.
- **Секретом стал пароль, а не вся строка подключения.** Достаточно положить
  `SUPABASE_DB_PASSWORD` в Environments → staging — ref проекта, имя
  пользователя пулера и хост workflow подставляет сам, пароль кодирует сам.
  Это закрывает все четыре ошибки, на которых деплой уже спотыкался: чужой
  проект, имя пользователя без ref, Direct connection вместо пулера и
  непроцентованный пароль. `SUPABASE_DB_URL` продолжает работать как запасной
  путь, с проверкой, что строка ведёт в нужный проект.
- По итогам аудита конвейера: ручной `workflow_dispatch` разрешён только с
  `main` (иначе он обходил `needs`), деплой ждёт и `app` — там Vitest-зеркала
  SQL-логики, — гейт по проекту сравнивает разобранный ref, а не подстроку
  всей строки, `supabase/setup-cli` ставится до появления строки подключения
  в окружении джоба, шаг «Что будет применено» показывает `db push --dry-run`,
  состояние после применения печатается и при падении, у всех джобов
  `timeout-minutes`. В Playwright в CI один повтор и таймаут 90 с; `parent`
  идёт строго после `teacher`, потому что оба читают одну неделю фикстуры.
- README описывал снятый механизм `workflow_run` и вёл к секрету
  `SUPABASE_DB_URL` через Direct connection — ровно тому, что ломало деплой.
  Раздел переписан под текущий конвейер. `.env.example` и README называли
  ключ Supabase по-разному; теперь оба имени, приложение читает любое.
  У обоих workflow `permissions: contents: read`.

### Безопасность

- `0044_attendance_comment_privacy.sql` — родитель больше не читает
  свободный текст к отметке посещения: с `attendance` снята
  `attendance_parent_read` (решение владельца 20.09.2026, тот же класс,
  что заметки о семье у бухгалтера в 0031). Что родителю нужно, отдаёт
  `student_attendance_brief()` (0043) — дата, статус, признак пропуска,
  без `comment`/`price_tiyin`/`subscription_id` физически.
- `0031_finance_notes_privacy.sql` — бухгалтер больше не читает свободный
  текст о семье и занятии: с `students`, `payers`, `lessons`, `attendance`
  снята `tenant_finance_select` (отменяет Р5 из 0028 по решению владельца
  17.09.2026). Что бухгалтеру нужно, отдают definer-функции без этих
  колонок: `students_brief()`, `payers_brief()` (источник экранов),
  `revenue_facts()` (источник `revenue_by_*`), `student_debts()` (долг в
  `student_balance`, строки — из `students_brief()`),
  `month_open_lessons_count()` — тот же запрос, что в `close_month`, вместо
  подсчёта «только planned» на вкладке «Периоды». Полный список политик
  новых ролей — `tests/0031` (из 0028). `/app/schedule` и блок «Занятий
  сегодня» бухгалтеру закрыты; `/app/students`, карточка ученика и
  `/app/finance` читают ученика и плательщика через новые функции.
- `0007_lock_down_participant_functions.sql` — сняты гранты у `public`, `anon`
  и `authenticated` с четырёх служебных функций: `rebuild_lesson_participants`,
  двух триггерных функций состава и `lesson_slot_conflicts`. В `0006` строка
  `revoke ... from public, anon` не сняла грант с `authenticated`, а Supabase
  выдаёт его по умолчанию — функции остались доступны любому залогиненному
  пользователю через `/rest/v1/rpc/`. Опаснее прочих было
  `rebuild_lesson_participants`: `security definer` без проверок, принимает
  произвольный `lesson_id` и в тексте исключения возвращает ФИО ребёнка —
  оракул по именам между тенантами. Нашёл линтер Supabase после применения
  `0006`. Там же — guard по `pg_trigger_depth()` внутри функции, чтобы
  неосторожный `grant` в будущем не открыл её снова.
- `tests/0007_function_grants.test.sql` — «забор» по `has_function_privilege`:
  для каждой из трёх ролей зафиксирован белый список исполняемых функций.
  Любая новая функция ломает тест, пока автор явно не решит, кому она видна.
- `tests/rls_smoke.test.sql` — под каждой ролью простой `select` из каждой
  таблицы с RLS. Список таблиц берётся из `pg_tables`, поэтому таблица из
  будущей миграции попадает под проверку сама. Ловит рекурсию политик,
  вызов функции, объявленной ниже по файлу, и таблицу без RLS.
