# Бизнес-правила

Что система не даёт сделать и почему. Одно правило — одна строка смысла,
рядом — **чем оно держится**: констрейнт, политика RLS или проверка внутри
`security definer`-функции.

Это не пересказ планов из [Roadmap/stages.md](Roadmap/stages.md), а
инвентаризация того, что **уже написано в миграциях**. Если правило здесь
есть, а в базе его нет — врёт этот файл, и чинить нужно его.

Пополняется по этапам — см. Definition of Done в
[Roadmap/stages.md](Roadmap/stages.md). Сейчас заполнены этапы 0–2 и 5;
расписание и абонементы (этапы 3–4, в схеме уже есть) — долг, въезжает
строками своего этапа при его закрытии.

**Почему важно, чем держится.** CLAUDE.md: «Инвариант — это констрейнт или
триггер, а не проверка в функции». Проверку в plpgsql обходят прямой
insert, изменение связанной строки, действие задним числом и параллельная
транзакция. Поэтому в колонке «держится» видно цену правила: констрейнт
не обойти ничем, политику — только через `security definer`, а проверку в
функции — любым путём, который эту функцию не зовёт.

## Сквозное

| Правило | Держится |
|---|---|
| Ничего не удаляется — только `deleted_at`. Исключение одно: `revoke_membership` делает настоящий `delete from memberships`, потому что отозванный доступ не должен оставлять строку, по которой RLS пустит обратно | Конвенция `docs/Database.md`; `apply_tenant_rls` добавляет `deleted_at is null` в `using` |
| Текущий центр берётся из JWT (`app_metadata.center_id`), роль — из таблицы `memberships` при каждом заходе. Не наоборот: членство могли отозвать, пока токен жив | `current_center()`, `role_in()`, `my_role()` — `0001_foundation.sql:78–123`; чтение роли на входе — `apps/web/app/app/layout.tsx:36` |
| Роль проверяется в SQL, а не в React. Ветвление в интерфейсе — про удобство, а не про безопасность: PostgREST отдаёт таблицу прямым запросом | Политики RLS на каждой таблице + гейты в RPC |
| Деньги — `integer` в тыйынах, никаких float | Типы колонок `*_tiyin` |
| Каждое бизнес-событие уходит в `events` (outbox), а не в сторонний сервис напрямую | `emit_event()` — `0001_foundation.sql:327` |
| Всё, что меняет строку, попадает в `audit_log` | `apply_audit(tbl)` — `0001_foundation.sql:290` |

## Этап 0 — центр, роли, доступ

| Правило | Держится |
|---|---|
| Центр нельзя создать прямым `insert` — только через `create_center()`, и тот, кто его создал, становится `owner` | Политик `for insert` на `centers` нет вовсе — `0001_foundation.sql:359–372` |
| Центр нельзя удалить через API: ни политики `for delete`, ни RPC | Там же |
| Настройки центра правит только владелец. Администратор — нет | `centers_update_owner`: `role_in(id) = 'owner'` — `0001:364` |
| Свою строку членства видит каждый; все строки центра — только владелец и администратор | `memberships_select_self_or_admin` — `0001:374` |
| `audit_log` и `events` видны только владельцу и администратору своего центра | `audit_log_select_admin`, `events_select_admin` — `0001:387`, `0001:394` |
| Роль в центре — одна из шести: `owner`, `admin`, `teacher`, `parent`, `registrar`, `finance` (две последние — этап 5, см. ниже) | `check (role in (...))` на `memberships.role` — `0001:60`, расширен `0026` |
| Базовая политика любой таблицы — «свой центр И роль owner/admin». Специалист и родитель получают доступ только отдельными политиками, которые пишутся явно | `apply_tenant_rls(tbl)` — `0004_staff.sql:24–48` |
| Пользователь без членства и пользователь с отозванным доступом — разные случаи, и он видит разные экраны | `was_access_revoked()` — `0005_students.sql:468`; `apps/web/lib/access.ts` |

## Этап 1 — сотрудники и приглашения

| Правило | Держится |
|---|---|
| Нельзя отключить последнего владельца центра | `revoke_membership` — `0004_staff.sql:265` (errcode 23514) |
| Владельца отключает только владелец. Администратор — нет | `revoke_membership` — `0004:261` |
| Администратор может назначить только роль специалиста: ни `owner`, ни `admin`, ни `parent`. Иначе он повышает себя до владельца через подставного пользователя | `change_member_role` — `0004:318` |
| Администратор не может пригласить администратора — та же причина | `create_invitation` — `0004:396` |
| Пригласить `owner` нельзя вообще, ни от чьего имени: владелец появляется только созданием центра или повышением через `change_member_role` | `create_invitation`: `p_role in ('admin','teacher','parent')` — `0004:391` |
| Отзыв доступа у специалиста деактивирует его карточку и отвязывает профиль, но карточку не удаляет — на ней висит история занятий | `revoke_membership` — `0004:274` |
| Приглашение живёт 7 дней и срабатывает один раз | `expires_at default now() + interval '7 days'`, `accepted_at` — `0004:108–130` |
| Единственный секрет приглашения — токен (48 hex-символов). По ссылке до входа видно только название центра, роль и срок | `invitation_preview()` отдаёт три поля и выдана `anon` — `0004:140–167` |
| Неизвестный токен не отличим от чужого или просроченного: ответ одинаковый | `invitation_preview` — `0004:140` |
| Специалист видит в списке сотрудников только собственную строку | `teachers_read_self` — `0004:96`; `staff_view` — `0004:482` |
| Приглашение с ролью `teacher` без указания карточки заводит её сам, сразу неактивной — до принятия приглашения специалист не занимает место в расписании | `create_invitation` — `0004:404` |

## Этап 5 — финансы и зарплата

| Правило | Держится |
|---|---|
| Роли `registrar` (стойка: ученики, плательщики, расписание, посещения, абонементы, платежи и рассрочки — без зарплаты и расходов) и `finance` (платежи, расходы, зарплаты, периоды — без клинических данных) добавлены к `owner`/`admin` | `can_front_desk()`/`can_finance()`/`can_payments()` — `0026_roles_registrar_rpc.sql:70,88` |
| Знак суммы — часть данных, не отдельный флаг: `payment` только положительный, `refund` только отрицательный, `correction` — любой | `payments_sign_matches_kind` — `0013_finance_core.sql:226` |
| Платёж не редактируется задним числом: ни сумма, ни дата, ни привязка к абонементу — только комментарий. Единственный путь записи денег — `record_payment` | `revoke all … grant update (comment)` — `0013:265–266` |
| `subscriptions.paid_tiyin` не может уйти в минус и не пишется напрямую — только пересчётом из `payments` | `subscriptions_paid_not_negative` — `0013:275`; `payments_recalc_paid` — `0013:341` |

| Бухгалтер не читает свободного текста о семье и занятии: `students.notes`/`custom_fields`, `payers.notes`/`custom_fields`, `lessons.notes`/`cancel_reason`/`custom_fields`, `attendance.comment`; ученики и плательщики приходят ему без этих колонок | снята `tenant_finance_select` с четырёх таблиц — `0031_finance_notes_privacy.sql`; `students_brief()`/`payers_brief()` без колонок физически; забор по `pg_policies` — `tests/0031` |
| Открыть закрытый месяц заново может только владелец | `reopen_month` — `0014:464` |
| Ставка специалиста не редактируется и не удаляется — новая запись с `valid_from` перекрывает старую; не больше одной ставки на комбинацию специалист/услуга в один день | `teacher_rates_no_same_day_conflict` — `0017_teacher_rates_and_salary.sql:448–449` |
| Утверждённая зарплата — неизменяемый снимок: не редактируется, не удаляется; переутверждение того же месяца — только через явную отмену владельцем | `salary_runs_immutable` — `0029_salary_runs_and_payment_date.sql:62`; `cancel_salary_run` (owner) |

| Возврат абонемента реально возвращает не больше внесённого — стоимость неотработанных занятий и деньги на руках часто разные числа при частичной оплате | `refund_subscription`: `least(refund_calc, paid_tiyin)` — `0030_refund_payment_and_overpay_guard.sql` |

## Известные слабые места

Не «баги», а места, где правило держится слабее, чем кажется. Проверять при
каждом изменении рядом.

- **Часть записей идёт прямым `update`/`insert` из server actions, без RPC**:
  карточка ученика (`students/actions.ts:93`), отмена приглашения
  (`settings/staff/actions.ts:102`), услуги, кабинеты, группы и состав групп
  (`settings/services/actions.ts`), статусы посещения и типы абонементов
  (`settings/*/actions.ts`). Их держит только RLS `tenant_admin` — то есть
  «свой центр + owner/admin», без дополнительных проверок. Для этих таблиц
  этого достаточно, но новая колонка с особыми правилами (например, «цена
  не меняется после продажи») через такой путь пройдёт молча.
- **Ни один server action не проверяет роль на стороне Next.js.** Это
  сознательно — источник истины в SQL, — но означает, что `redirect('/app')`
  на странице косметический: настоящий отказ приходит из базы.
- **`owner` и `admin` в интерфейсе почти неразличимы.** Разница живёт в трёх
  местах: `lib/roles.ts` (кого можно назначить и пригласить),
  `staff-table.tsx:30` (администратор не трогает владельца) и RLS на
  `centers` (настройки центра). Везде остальное — `role === 'owner' || role === 'admin'`.
