# AGENTS.md — правила для AI-инструментов в этом проекте

Этот файл читают Claude Code, GitHub Copilot и любой другой AI-помощник
перед тем как менять код. Если что-то здесь противоречит твоей интуиции —
следуй этому файлу, не общим лучшим практикам.

## Проект

CRM для частнопрактикующего логопеда (Бишкек), MVP на одного пользователя
с прицелом на multi-tenant SaaS в будущем (пока не реализовано).

## Стек — именно этот, не предполагай другой

- Next.js 14, App Router, TypeScript
- Supabase: Postgres + Auth + Storage — доступ через `@supabase/supabase-js`
  и `@supabase/ssr` напрямую (клиенты в `shared/services/supabase/`)
- **Prisma НЕ используется.** Никакой ORM, кроме Supabase-клиента.
- Tailwind CSS для стилей
- Хостинг: Vercel (автодеплой при push в `main`)
- Архитектура: Feature-First (`app/`, `features/<name>/`, `shared/`)

## Обязательно прочитать перед изменением кода

1. `docs/Requirements.md` — что вообще должна делать система
2. `docs/Database.md` — актуальная схема БД (сверяй с реальными миграциями
   в `database/`, документ может отставать от кода)
3. `docs/Decisions.md` — почему стек и архитектура именно такие
   (например: почему нет AI/n8n/WhatsApp API в MVP — это осознанный выбор,
   не забытая задача)

## Правила

- **Не меняй схему БД без явного объяснения** — какая миграция добавляется,
  зачем, и как это соотносится с уже существующими таблицами.
- **Не удаляй существующую функциональность**, если явно не попросили.
- **Не дублируй бизнес-логику.** Если что-то похожее уже есть в другой
  фиче — переиспользуй или явно спроси, почему нужна отдельная реализация.
- **RLS (Row Level Security) обязателен на каждой новой таблице.** Это
  проект с персональными данными детей — доступ строго по
  `therapist_id = auth.uid()` (напрямую или через цепочку JOIN).
  Ничего не открывай публично без явного запроса.
- **Один источник правды на одну сущность.** История проекта: Copilot
  один раз создал параллельную систему учёта оплат (ledger) рядом со
  старым полем `sessions.is_paid`, не связав их — это привело к
  рассинхронизации цифр на дашборде. Перед добавлением новой таблицы/поля
  проверяй, не дублирует ли она то, что уже есть.
- **Не роняй всю страницу необработанной ошибкой.** Если что-то не
  найдено/не принадлежит пользователю — это штатная ситуация
  (`notFound()`, пустой список, редирект), а не повод для голого `throw`
  в Server Component.

## Перед тем как сказать, что задача выполнена

1. Прогнать `npm run build` — должно собираться без ошибок.
2. Прогнать `npm run lint`.
3. Проверить, что RLS-политики есть на всех новых/изменённых таблицах.
4. Если менялась схема БД — файл миграции лежит в `database/` со
   следующим номером по порядку (`00N_описание.sql`), и обновлён
   `docs/Database.md`.

## После изменения кода — всегда показать

- Список изменённых/созданных/удалённых файлов
- Что именно исправлено/добавлено и почему
- Если менялась БД — SQL миграции текстом, не только "выполнено"

## Если задача большая — сначала план, потом код

Не бросайся сразу писать код на многошаговую задачу. Сформулируй короткий
план (какие файлы затронет, какие есть риски, нужна ли миграция БД) и
дождись подтверждения, прежде чем реализовывать.

## Git

Коммиты — на русском, коротко и по сути (`добавлена форма входа`, не
`feat: add login form`). Одна логическая правка — один коммит, не мешать
несвязанные изменения в одном коммите.
