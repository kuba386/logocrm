# CLAUDE.md

Правила работы над LogoCRM. Здесь только то, что применимо к **любому**
этапу. Спека конкретных этапов — `docs/Roadmap/stages.md`.

Всё, что записано ниже, уже нарушалось хотя бы раз и стоило переделки.

## Процесс

- Источник истины по плану — `docs/Roadmap/stages.md`. Читай его сам, не
  спрашивай содержание этапа.
- **Перед написанием миграции покажи план субагенту `architect`.** Он
  проверяет схему и границы доступа по списку уже допущенных ошибок.
- Схема меняется **только файлами** в `packages/db/supabase/migrations`.
  Supabase MCP — на чтение. Применяет миграции CI через `deploy-staging`.
- Миграции неизменяемы после мержа. Ошибку исправляет следующая миграция.
- Ни одного мержа без зелёного джоба `db`: pgTAP — это проверка прав
  доступа к данным детей, а не формальность.
- Отчёт по этапу — `reports/stage-N.md` по шаблону. Обязательны разделы
  «Что это даёт» и «Отступления от ТЗ».
- К владельцу приходить, только когда решение не выводится из спеки.

## База

- Конвенции таблиц, `apply_tenant_rls`, `apply_audit` — `docs/Database.md`.
- **Инвариант — это констрейнт или триггер, а не проверка в функции.**
  Проверку в plpgsql обходят прямой insert, изменение связанной строки,
  действие задним числом и параллельная транзакция.
- **NULL в `EXCLUDE` не конфликтует.** Если колонка nullable — продумай,
  что происходит, когда она пуста.
- **Политика, ссылающаяся на другую таблицу с RLS, ходит через
  `security definer`-функцию.** Иначе `infinite recursion detected in
  policy`, и ломается не только новая таблица. Функция объявляется рядом с
  таблицей, которую читает, а не в разделе про политики.
- **Денормализованные таблицы закрыты на запись.** Заполняются триггерами,
  грант только `select`, политик на запись нет ни у кого.
- **Роль проверяется в SQL.** Ветвление в React не защищает: PostgREST
  отдаёт таблицу прямым запросом.
- **Каждая `security definer`-функция** начинается с проверки
  `auth.uid() is not null` и прав на конкретный `center_id`.
- **Каждая функция заканчивается явными грантами**: `revoke ... from public,
  anon` и `grant ... to authenticated`. Postgres выдаёт `EXECUTE` роли
  `PUBLIC`, а Supabase — ролям `anon` и `authenticated`; снимать нужно оба.
- **После каждой миграции — линтер Supabase** (`get_advisors` или вкладка
  Advisors). pgTAP ходит от `authenticated` и грантов не проверяет.
- Деньги — `integer` в тыйынах. Никаких float.
- Ничего не удаляется, только `deleted_at`.
- Статусы — lookup-таблицы, не `enum`.

## Приложение

- **Ошибки разбираются в одном месте** — `apps/web/lib/errors.ts`. Компоненты
  не парсят ошибки у себя: иначе один конфликт покажется тремя текстами, а
  новый вызов забудут обработать.
- **Оптимистичного UI нет.** Только ответ сервера. Иначе при отказе запись
  появится и исчезнет — на общем экране это читается как баг базы.
- **Время рендерится в часовом поясе центра**, не браузера:
  `centers.settings->>'timezone'`, дефолт `Asia/Bishkek`. Администратор из
  поездки должен видеть расписание студии.
- **Никаких прямых `update` в обход функций**, если для действия есть RPC.
  Ошибка должна приходить в одном формате со всеми остальными действиями.
- **Занятость, права и деньги в браузере не считаются.** Всегда из RPC. Два
  источника истины разъедутся, и интерфейс покажет «свободно» там, где база
  откажет.
- Одна страница на все роли, ветвление внутри. Отдельные страницы под
  admin/teacher/parent разъедутся через два этапа.
- Список за период — один запрос на диапазон, не N запросов по дням.
- Все тексты интерфейса и ошибок — на русском.

## Дублирование логики между SQL и TypeScript

Иногда логика нужна в обоих местах — например календарь серии занятий.
Тогда:

- **SQL — источник истины, TypeScript — зеркало** для мгновенной подсказки.
- Меняешь одну реализацию — меняешь обе.
- Общий набор случаев прогоняется и в Vitest, и в pgTAP, с одинаковыми
  входными данными.

## Окружение

- Docker на машине разработки нет: локальный `supabase start` и `pnpm db:test`
  недоступны. pgTAP гоняет CI.
- **Не запускать `pnpm build`, пока работает `pnpm dev`** — общий `.next`
  ломает дев-сервер.
- Cookie привязаны к хосту, а не к порту. Старый MVP на `localhost` и
  LogoCRM на `127.0.0.1` — иначе сессии конфликтуют.
- Секреты, тумблеры в дашборде, `gh auth login` и prod — только руками
  владельца.

## Хуки

Два правила выше держатся не только на честном слове — они проверяются
автоматически (`.claude/settings.json`, скрипты в `.claude/hooks/`):

- **`no-build-while-dev.mjs`** — `PreToolUse` на `Bash`. Если порт из
  `.claude/launch.json` (плюс 3000 и 3100) слушается, любая команда сборки
  отклоняется. Для проверки кода есть `pnpm typecheck` и `pnpm lint`.
- **`applied-migration-guard.mjs`** — `PreToolUse` на `Edit|Write`. Правка
  файла в `packages/db/supabase/migrations/`, который уже есть в
  `origin/main`, требует подтверждения: схема катится в staging из `main`,
  значит такая миграция уже применена и правка разведёт файл с базой.

Оба на `node` — `jq` на машине нет. Проверить или отключить: `/hooks`.
